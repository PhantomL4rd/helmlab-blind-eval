# data/retest/

The 2026 blind human-perception retest: for each of colorant-picker's 64 traditional-color
targets, which FF14 dye looks closest to a human eye? Collected independently of any
color-distance algorithm — see the top-level `README.md` for the tool and workflow, and
`../README.md` for how this relates to `existing-human-judgments/`.

```
snapshot/
  raw/      full-fidelity copy of colorant-picker's dyes.json + traditional-colors.json,
            frozen at retest start — see raw/PROVENANCE.md. Includes dyeId; never fetched by
            the eval app.
  blind/    derived, blind-safe views the eval app actually fetches (id+hex only, no dyeId,
            no name/tags during evaluation) — generated by `npm run snapshot`.
sessions/   one file per evaluation session (data/retest/sessions/{sessionId}.json), written
            immediately on every answer. The actual working data — not regenerable, keep it.
exports/    human-picks.json / targets.json / dyes.json / evaluation-sessions.json /
            methodology.md, ready to hand off. Generated from sessions/ + snapshot/blind/ —
            regenerate anytime with `npm run export` (or via the eval app's export view).
```

## Why no algorithm ever pre-filters the candidate pool

An earlier design used a union of several color-distance metrics' top-N to narrow ~125 dyes
down to a manageable per-target shortlist before showing them to a human. That was rejected:
even a union of multiple algorithms still lets algorithms decide what a human is allowed to
choose from, which weakens independence as an external benchmark. Instead:

- **Phase 1 (explore)**: the evaluator sees the *entire* candidate pool (currently 97 dyes —
  metallic+vivid tags excluded, the same pool the current `dyeId` is chosen from) laid out by
  hue only, and builds their own shortlist by eye. No target-to-candidate distance of any kind
  informs this pool or its layout.
- **Phase 2 (refine)**: only within the evaluator's own shortlist does side-by-side comparison
  happen, in randomized order.

This keeps the *shortlisting* decision — which is where an algorithm's blind spots would
otherwise creep in — entirely human, while keeping the *comparison* step focused enough to be
usable across 64 targets.

## What's recorded per target

Not just the final pick: `availableDyeIds` (what Phase 1 showed — the whole pool, so identical
on every record in a session), `shortlistedDyeIds` and `shortlistHistory` (what the evaluator
built and how), `candidateDisplayOrder` (the actual Phase 2 order shown), `selectedDyeId` and
`selectionHistory`, `ties`, `confidence`, `uncertain` (no plausible candidate found), and Phase
1/2 timestamps. See `src/lib/types.ts` (`TargetRecord`) for the raw session-file shape kept
under `sessions/`.

The `human-picks.json` export (`exports/`) is a cleaned-up derived view for handoff: every
dye-referencing field (`selectedDyeId` → `selectedDyeHex`, etc., including inside
`shortlistHistory`/`selectionHistory`) is resolved to hex instead of the FF14-internal id
(lossless — hex is unique across the pool), and `availableDyeIds` is dropped since it's the
same ~97-dye pool on every record (see the accompanying `dyes.json` export instead). The raw
session files under `sessions/` keep the original ids and are never modified by exporting.

## Multiple sessions per evaluator

`sessionId` is independent of `evaluatorId` — the same evaluator can start a brand-new session
at any time (e.g. to retest after a gap), and each session is recorded and exported separately.
This is what lets `analysis.html` (once supported) compare a single evaluator's agreement with
themselves over time, not just across evaluators.

## Blindness — what's guaranteed and what isn't

During Phase 1/2, only `snapshot/blind/targets.blind.json` and `dyes.blind.json` (id+hex) are
fetched — never dye names/tags, never `dyeId`, never any algorithm's score or rank. Names are
revealed only in the export view, after answers are already recorded, and only
`analysis.html` (a separate bundle, never imported by the eval app) reads `dyeId`. This is a
good-faith design for a local, single/few-evaluator tool, not a defense against an evaluator
who deliberately inspects network requests or navigates to `snapshot/raw/` or
`snapshot/blind/dyes.full.json` directly.
