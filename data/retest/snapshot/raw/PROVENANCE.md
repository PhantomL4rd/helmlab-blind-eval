# Data source — this is the frozen evaluation-time snapshot

`dyes.json` and `traditional-colors.json` in this directory are a **full-fidelity, unmodified
snapshot copy**, not a live reference, of the corresponding files in
[`PhantomL4rd/colorant-picker`](https://github.com/PhantomL4rd/colorant-picker), taken at the
moment the 2026 retest evaluation round began.

- Source commit: `7a94d555a6879d05e2b2f3afc559724315790d0b`
- Source commit date: 2026-07-20T14:29:13+09:00
- Snapshot taken: 2026-08-27
- Source paths: `static/data/dyes.json`, `static/data/traditional-colors.json`
- Counts at snapshot time: 125 dyes, 64 traditional-color targets

**This snapshot is deliberately never overwritten**, even if colorant-picker's own data changes
later — the whole point is to preserve exactly what was being compared at evaluation time (see
the top-level README's "why a frozen snapshot" note). If a *new* retest round is run against
newer colorant-picker data, copy the updated files into a new dated snapshot directory instead
of replacing this one.

`traditional-colors.json` here still carries the `dyeId` field from the source repo. This is the
**current production algorithmic mapping, not a human judgment** — see the top-level
`README.md`'s "algorithmic-baseline vs. human judgment" section for why (short version: it's
generated by `scripts/sync-traditional-color-dyes.mjs` via CIEDE2000/OKLab + a helmlab
fallback; the 3-of-4 mismatch against `data/existing-human-judgments/issue3-followup.json`
is the concrete evidence). It must never be read by the
blind eval app (`index.html` / `src/App.svelte` and everything under `src/lib/` it imports) —
only `scripts/snapshot-data.mjs` (to build `data/retest/snapshot/blind/targets.blind.json`,
which strips `dyeId` down to `id`/`reading`/`hex`) and `analysis.html` / `src/Analysis.svelte`
(the post-hoc, algorithmic-baseline comparison view, used strictly after a retest session is
complete) may read `dyeId` from this file.
